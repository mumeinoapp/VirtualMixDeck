# VirtualMixDeck（仮称）設計メモ

## コンセプト

Stream Deckのような、どんなショートカットも自由に登録できる超軽量アプリ。
アプリ・ブラウザなど個別に細かく音量調整できる機能を搭載し、OBS連携で「個別調整した音声」を配信にもそのまま反映できるようにする。

## 確定した全体構成

1. **ショートカット登録エンジン**（2026-08-12 基本方針決定）
   - グローバルホットキー／ボタングリッドUIで任意のアクション（アプリ起動、URL開く、ホットキー送信、音量操作、OBS操作など）を登録
   - Stream Deck等の類似デバイスの「ボタン配置」は参考にするが、UI/デザイン自体はオリジナルにする
   - **グリッド構造**：まずは固定グリッド＋複数ページ切替え方式（Stream Deck型）で実装。将来「自由レイアウト（ボタンサイズ・位置自由）」へ拡張したいという要望あり
     - 拡張性を保つため、データモデルは**アクション定義とレイアウト情報を分離**して設計する：各ボタンは `{ id, action: {...}, page, row, col }` の形とし、`action`（何をするか）と配置情報（`page/row/col`）を独立フィールドにする
     - 将来自由レイアウトへ移行する場合は`row/col`を`x/y/width/height`に置き換えたレイアウト情報を追加するだけで済み、`action`側のスキーマ・実行エンジンは変更不要（移行はレンダラーのUIコンポーネント差し替えが中心になる想定）
   - **実装するアクション種類**（全て実装予定。実装順はおまかせされ、以下の順を予定）：
     1. アプリ起動／URL開く（外部依存なしで最も単純、最初に着手）
     2. ローカル／配信音量操作（🎧/📡、VirtualMixDeckの中核機能。.NETヘルパー＋OBS WebSocketの両方を使う）
     3. OBS操作（シーン切替え・配信開始/停止等。検証済みのOBS WebSocket基盤をそのまま流用）
     4. ホットキー送信（他アプリへのキー入力代行）。**方式決定（2026-08-12）**：ローカル音量制御用に採用する小型.NETヘルパープロセス（`VirtualMixDeck.Helper`想定）に統合し、Win32 `SendInput` APIでキー入力を送る。nut-js等の追加ネイティブnpm依存は増やさず、既存の1本のヘルパープロセスに機能追加する形にする（アーキテクチャの一貫性・配布の単純さを優先）

2. **個別音量調整（ローカル側）**
   - Windows Core Audio API（`ISimpleAudioVolume`）でプロセス単位のセッション音量を取得・調整
   - ブラウザはタブ単位ではなく「プロセス単位」までが現実的な粒度（既定路線として合意済み）

3. **OBS連携（配信側）**
   - OBS WebSocket（v5）経由で「アプリケーション音声キャプチャ」ソースの`volume`/`mute`を操作
   - OBSが未起動/未接続の場合、配信側フェーダーは無効化表示にする（合意済み仕様）

## 核心の設計要件：ローカルと配信の音量を完全に独立させる

やりたいこと：
- 「自分に聞こえてる音量を下げても配信上の音量は下がらない」
- 「自分に聞こえてる音量は下げずに配信上の音量だけ下げる」
- この2つを、アプリ単位で独立した2本のフェーダー（🎧ローカル / 📡配信）として提供する

### 実機検証で確認した事実（2026-08-12実施）

Windows実機・OBS 32.1.2で以下を検証し、**確認済み**：

- OBSの「アプリケーション音声キャプチャ（ベータ版）」ソースでChromeの音声を取得
- PowerShell + C# COM interopでWindows Core Audio API（`ISimpleAudioVolume.SetMasterVolume`）を直接叩き、ChromeプロセスのWindowsセッション音量を`0`に設定
- **その状態でもOBS側のメーターは全く減衰せず、フル音量のまま振れ続けた**

→ **OBSのアプリケーション音声キャプチャは、Windowsの音量ミキサー（セッション音量）と完全に独立して動作している**ことが実証された。

### 結論・実装方針

- ローカル側：Windows Core Audio API（`ISimpleAudioVolume`）でセッション音量を操作
- 配信側：OBS WebSocket経由でアプリケーション音声キャプチャソースの`volume`/`mute`を操作
- 両者は別API・別経路なので、特別な工夫（仮想オーディオデバイス等）なしに「独立した2本のフェーダー」がそのまま実現できる

検証に使ったCOM interopコードは [`research/AppVolume.cs`](../research/AppVolume.cs) に保存（`ISimpleAudioVolume`でプロセス単位のセッション音量を取得・設定する最小実装。将来のローカル音量調整機能の土台として流用可能）。

## OBS側セットアップの自動化（2026-08-12 実機検証済み・確認）

`obs-websocket-js`（v5プロトコル）でOBS 32.1.2（WebSocketサーバー有効化・ポート4455）に接続し、以下を確認：

- `CreateInput`（`inputKind: "wasapi_process_output_capture"`）で、**ユーザーの事前手動セットアップなしに**アプリケーション音声キャプチャソースを現在のシーンへ自動作成できる（`inputSettings: {}`でOK、後から設定変更可能）
- 作成後に`GetInputPropertiesListPropertyItems`（`inputName`指定・`propertyName: "window"`）を呼ぶと、現在起動中の全ウィンドウの選択肢が`itemValue`として返る。フォーマットは`"ウィンドウタイトル:ウィンドウクラス名:プロセス名.exe"`（例: `"Claude:Chrome_WidgetWin_1:claude.exe"`）
- `SetInputSettings`で`{ window: "<上記itemValue>" }`を渡すことで、キャプチャ対象プロセスをコード側から選択できる
- `SetInputVolume`（`inputVolumeDb`）・`SetInputMute`で配信側音量・ミュートも操作可能（既知）
- `RemoveInput`で後片付けも可能（一時ソースのクリーンアップに使える）

→ **結論：OBS側の事前手動セットアップは完全に不要にできる。** アプリ起動時またはボタン登録時に、対象アプリのプロセス名からWindow一覧を検索してマッチするものを選び、`CreateInput`→`SetInputSettings`で配信側キャプチャを自動構築するフローが実装できる。

検証コードは `research/obsws-createinput-test.js` に保存（Node.js + `obs-websocket-js@5`）。

### 実装上の留意点（未確定・要検討）

- `window`プロパティの選択肢はプロセス名だけでなく「起動中の具体的なウィンドウ（タイトル込み）」単位で列挙される。対象アプリのウィンドウタイトルが動的に変わる場合（ブラウザのタブ切り替え等）、`itemValue`の完全一致ではなく`プロセス名.exe`部分でのマッチングが必要になりそう
- アプリ未起動時（ウィンドウが存在しない）はwindowプロパティの選択肢に出てこないため、「アプリ起動を検知してから`CreateInput`する」フローが必要
- 複数ウィンドウを持つプロセス（例: Chrome複数タブ／ウィンドウ）の場合、どのウィンドウを選ぶかのUI/ロジックが必要（既定路線の「プロセス単位」と若干のズレがあるため要相談）

既存のStream Deck向け音量プラグイン（公式Volume Controller、AudioMixer、FocusVolumeControl等）を調査した限り、いずれもWindows音量ミキサー操作のみで、「ローカル/配信の独立制御」を実現しているものは見当たらなかった（差別化ポイント、[[project-streammixdeck]]参照）。

## 技術スタック（2026-08-12 決定）

MultiCastDeck（同ユーザーの既存Electronアプリ）の基盤をそのまま流用する方針で確定：

- **Electron**（main / preload / renderer構成）＋ **electron-store**（設定永続化）＋ **electron-builder** / **electron-updater**（配布・自動更新、GitHub Releases）をMultiCastDeckからそのまま踏襲
- **グローバルホットキー**：Electron標準の`globalShortcut` APIで追加依存なし
- **OBS連携**：`obs-websocket-js`（v5プロトコル）。`research/obsws-createinput-test.js`で動作確認済み
- **ローカル音量制御（Windows Core Audio API）**：**小型.NETヘルパープロセス方式に決定**
  - 検証済みの`research/AppVolume.cs`（`ISimpleAudioVolume`によるプロセス単位セッション音量操作）をコンソールアプリとしてビルドし、Electronのmainプロセスから子プロセスとして起動、stdin/stdout経由のJSONコマンドでやり取りする
  - 却下した代替案：Node C++ネイティブアドオン（node-gyp/MSVCビルド環境・配布時のABI互換性管理が手間）／FFI経由でのCOM直接呼び出し（COMマーシャリングをJS側で手実装する必要がありバグらせやすい）
  - 採用理由：検証済みコードをほぼそのまま活かせて実装リスクが最も低いため

## .NETヘルパープロセス＋ブリッジ実装（2026-08-12 完了・動作確認済み）

`VirtualMixDeck/helper/`（`VirtualMixDeck.Helper`、.NET 10、`net10.0-windows`、`dotnet build`で生成）を実装：

- `AudioSessions.cs`：`AppVolume.cs`のCOM interopをベースに、`ListSessions()`／`SetVolumeByProcessName()`／`SetMuteByProcessName()`を実装（プロセス名で一致する全セッションに適用、複数プロセス一致時はまとめて適用）
- `HotkeySender.cs`：Win32 `SendInput`でキー送信。`"ctrl+shift+a"`のような文字列をパースして仮想キーコード列に変換し、down→up順で送信
  - **ハマりどころ（記録）**：`INPUT`共用体をC#の`[StructLayout(LayoutKind.Explicit)]`で`KEYBDINPUT`のみ定義すると24バイトになるが、ネイティブ側の`INPUT`共用体は`MOUSEINPUT`（x64で28バイト）が最大サイズなので28バイトに合わせないと`cbSize`不一致で`SendInput`が`ERROR_INVALID_PARAMETER(87)`で失敗する（実機で確認・修正済み）。同様のP/Invokeコードを書く際は要注意
- `Program.cs`：標準入力から1行1JSONコマンドを読み、`System.Text.Json`でパースして処理、標準出力に1行1JSONレスポンスを返すループ。対応コマンド：`ping`／`list_sessions`／`set_volume`／`set_mute`／`send_hotkey`

`VirtualMixDeck/app/src/helperBridge.js`：Electron側からヘルパーexeを子プロセスとして常駐起動し、`readline`でJSON行を受信、`id`ベースのPromise解決でリクエスト/レスポンスを対応付けるブリッジを実装。`main.js`の`executeAction`から`local_volume`（`set_volume`呼び出し）・`hotkey`（`send_hotkey`呼び出し）で使用。動作確認はNodeから`helperBridge.js`を直接呼び出す形で実施済み（Electron GUI越しのクリック確認はVirtualMixDeckがスタートメニュー未登録のcomputer-use対象外アプリのため未実施、次回可能なら実施）。

ヘルパーexeのパス解決は現状 `VirtualMixDeck/helper/bin/Debug/net10.0-windows/win-x64/VirtualMixDeck.Helper.exe` を直接参照する開発時専用の実装（`helperBridge.js`の`resolveHelperExePath()`）。**配布パッケージ時にはexeをelectron-builderのresourcesに含めてパスを切り替える対応が必要**（未実装）。

## OBS WebSocket連携実装（2026-08-12 完了・実機動作確認済み）

`VirtualMixDeck/app/src/obsBridge.js`を実装し、`main.js`の`stream_volume`／`obs`アクションに統合：

- `connect({url, password})`／`getStatus()`：接続状態を保持。接続設定は`electron-store`の`obsConnection`に保存し、アプリ起動時に自動接続を試みる（OBS未起動時は静かに失敗）
- `ensureInputForProcess(processName)`：`VMD_<processName>`という命名で`wasapi_process_output_capture`入力を（無ければ）自動作成し、`GetInputPropertiesListPropertyItems`で対象プロセスの起動中ウィンドウを検索して`SetInputSettings`で紐付ける（`research/obsws-createinput-test.js`のロジックを本実装に統合）
- `setVolume`／`setMute`：上記を確保した上で`SetInputVolume`（`inputVolumeMul`、0.0〜1.0）／`SetInputMute`
- `switchScene`／`startStream`／`stopStream`：それぞれ`SetCurrentProgramScene`／`StartStream`／`StopStream`をラップ
- レンダラーに「OBS設定」ボタン＋接続ダイアログ（URL・パスワード入力）、接続状態表示（ヘッダーの`OBS: 接続済み/未接続`）を追加
- ボタン編集ダイアログに`stream_volume`（対象プロセス名・音量、`local_volume`とフィールド共有）と`obs`（操作種類：シーン切替え/配信開始/配信停止、シーン名）の入力欄を追加

**実機検証済み**（Node直接呼び出しでobsBridge.jsをテスト、OBS 32.1.2 + WebSocket有効化状態で実施）：
- `setVolume('Discord', 0.7)` → OBS上に`VMD_Discord`ソースが自動作成され、`window`設定が`"@ぷるぅ - Discord:Chrome_WidgetWin_1:Discord.exe"`に正しく紐付けられ、`inputVolumeMul`が期待通り0.7（-3.1dB相当）に反映されることを確認
- `start_stream`／`stop_stream`は実際に配信が始まってしまうリスクがあるため意図的にテスト未実施（API呼び出し自体は検証済みのobs-websocket-js呼び出し規約に準拠しているため信頼度は高い）

これで4種類のアクション（アプリ起動/URL開く・ローカル/配信音量操作・OBS操作・ホットキー送信）全てが実装完了。ホットキー以外は全てNode直接呼び出しで実機動作確認済み。

### デバッグで判明した注意点（重要・記録）

- **この開発環境（リモート/仮想デスクトップ経由のcomputer-use自動化）では、OS側スクリーンショット取得がElectronウィンドウを黒い矩形として誤って表示することがある**（GPU compositorとリモート画面共有の間の既知の相性問題と推測、実際のアプリ描画は正常）。`SetForegroundWindow`で前面化してもズレは解消しないため、computer-useのスクリーンショットだけでは「アプリが壊れている」と誤判断しないよう注意。
  - **確実な検証方法**：Electron自身の`webContents.capturePage()`でPNGを直接保存し、Readツールで開いて目視する方が確実（本セッションではこの方法で正常描画を確認できた）。今後このアプリのUI変更を検証する際は、まずこの方法を使うこと。
  - 生のWin32 API（`MoveWindow`等）でウィンドウ位置を操作すると、Electronの内部レイアウトパイプラインとズレて描画が崩れることがある（実機で確認）。ウィンドウ位置を動かす必要がある場合はElectron自身のAPI（`win.setBounds`等）を使うこと。

- ブラウザは「タブ単位」ではなく「プロセス単位」まで（ローカル・配信とも同じ粒度）
